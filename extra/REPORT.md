## 附加题一：MNIST 手写数字分类替代实验

### 1. 目的与数据

用通用图像分类任务验证“PyTorch 训练 → ONNX 导出 → ONNX Runtime 推理”的完整流程，比较同一组权重在 CPU 上的预测一致性和耗时。该结果只能说明 MNIST 上的表现，不能推断其他数据域的识别准确率。

MNIST 为 0～9 共十类、28×28 灰度手写数字。使用 [Torchvision 官方数据集实现](https://docs.pytorch.org/vision/stable/_modules/torchvision/datasets/mnist.html)中列出的 OSSCI 镜像和四个 MD5 校验值。脚本直接下载、解析 IDX，不依赖 torchvision。原始文件、下载 URL、MD5 与 SHA256 均已保存。

从官方 60,000 张训练样本中按种子 `20261020` 固定随机划分 55,000 张训练、5,000 张验证；官方 10,000 张测试样本独立保留。仅以验证准确率挑选模型，不用测试集挑选超参数。保存划分索引，预处理为 float32 像素除以255，不做数据增强。

### 2. 网络与训练

结构：输入 `N×1×28×28` → 3×3 卷积（1→8，padding=1）→ ReLU → 2×2最大池化 → 3×3卷积（8→16，padding=1）→ ReLU → 2×2最大池化 → 展平784维 → 全连接32 → ReLU → 全连接10。输出 logits，交叉熵内含所需的归一化计算，不在网络末尾额外加 Softmax。

共有 **26,698 个可训练参数**。Adam，学习率0.001，batch=128，5轮，CPU训练4线程。选取验证准确率最高的一轮；本次为第5轮。训练循环（含验证和保存）约8.750秒，不含下载、解析、模型构建及导出。

| 轮次 | 训练损失 | 验证损失 | 验证准确率 |
|---|---:|---:|---:|
| 1 | 0.53253 | 0.19999 | 94.22% |
| 2 | 0.15874 | 0.11965 | 96.38% |
| 3 | 0.10630 | 0.09667 | 97.04% |
| 4 | 0.08509 | 0.08716 | 97.10% |
| 5 | 0.07308 | 0.07329 | 97.66% |

### 3. 导出与准确率

使用 [PyTorch ONNX 导出接口](https://docs.pytorch.org/docs/stable/onnx_export.html)，`dynamo=True`、opset18、单文件存储、动态 batch（导出约束1～256）。权重文件110,065字节，ONNX文件120,577字节。模型结构经 `onnx.checker` 验证。

| 指标 | 实测 |
|---|---:|
| PyTorch 测试正确数/总数 | 9,806/10,000 |
| ONNX Runtime 测试正确数/总数 | 9,806/10,000 |
| 两者测试准确率 | **98.06%** |
| 两引擎预测类别一致率 | **100%** |
| 全测试集 logits 最大绝对差 | 7.6294×10⁻⁶ |

全测试集通过 `rtol=1e-4, atol=1e-4` 的逐元素数值比较；另外检查 batch1和32。分类一致不要求浮点结果逐位相同，也不能保证任意新输入都完全一致。

### 4. CPU 推理速度

环境：Windows 11，Intel Core i9-14900HX（24核/32逻辑处理器），Python3.13.11，PyTorch2.14.1+cpu，ONNX1.23.2，ONNX Runtime1.31.0，NumPy2.5.4。

两引擎均CPU、FP32、算子内/间线程数为1。PyTorch为 eager 模式、`eval()`及`inference_mode()`，未使用 `torch.compile`。ORT仅启用 `CPUExecutionProvider`，顺序执行、开启图优化；线程设置依据 [ORT 官方线程说明](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)。

每种batch和引擎先预热100次，再计时5轮，每轮500次，每轮交替引擎先后顺序。输入是32个预加载批次循环使用；每项有2,500条耗时，合计10,000条原始记录。采用 `perf_counter_ns`；计时包含Python推理调用与结果返回，排除模型/会话加载、磁盘读取、输入归一化和预先完成的Tensor/NumPy转换。吞吐量按 `batch×1000/平均毫秒` 计算，是本微基准下的处理率。

| Batch | 引擎 | 平均耗时 ms/批 | 中位数 ms/批 | P95 ms/批 | 图片/秒 |
|---|---|---:|---:|---:|---:|
| 1 | PyTorch | 0.11667 | 0.10770 | 0.17131 | 8,571 |
| 1 | ONNX Runtime | 0.01817 | 0.01690 | 0.02230 | 55,034 |
| 32 | PyTorch | 1.74014 | 1.70105 | 2.14061 | 18,389 |
| 32 | ONNX Runtime | 0.23431 | 0.21970 | 0.30511 | 136,570 |

在本机、本网络和上述设置下，按平均耗时，ORT分别约为 **6.42倍（batch1）** 和 **7.43倍（batch32）** 的加速。可能原因包括静态计算图优化与算子执行开销差异，但本次没有算子级剖析，不能断言某一机制贡献的比例。未比较编译后的PyTorch，不表示所有模型或所有部署方式都有同样差距。

### 5. 误差分析与局限

测试错分194张。混淆矩阵中最多的误判为真实4→预测9（23张）；其次2→7、8→9各10张。数字8召回率95.48%，数字4为96.23%，数字0为99.49%，说明总体准确率会掩盖类别差异。这些计数说明模型易混淆哪些类别；未逐张人工归因，不能把所有错误都认定为笔迹相似。

训练和验证损失在五轮中均下降；这没有显示本次五轮内明显的验证损失反弹，但不能据此证明不存在过拟合。只运行一个随机种子，没有跨种子置信区间。MNIST的背景、分辨率与采集条件有限，不能证明真实场景的泛化能力。

测速为单进程、缓存较热的短时微基准。没有锁定CPU核心、频率或功耗状态，也没有测量功耗；操作系统调度、后台程序与温度均可能影响结果。P95是调用样本的分位数，不是统计置信区间。该速度不含图像采集等完整应用开销，不应称为整套系统的帧率。

## 附加题二：ARM/x86，NPU/GPU

ARM与x86首先是指令集架构家族，规定软件能使用的指令、寄存器等接口；它们并不直接代表某款芯片的速度或耗电。ARM通常归为RISC体系；x86通常归为CISC体系。现代芯片通过流水线、乱序执行、缓存及内部微操作实现复杂优化，所以不能仅用“指令简单/复杂”判断整机性能。[Arm架构介绍](https://www.arm.com/architecture/cpu)、[Arm关于ISA与能效的讨论](https://developer.arm.com/community/arm-community-blogs/b/architectures-and-processors-blog/posts/the-final-isa-showdown-is-arm-x86-or-mips-intrinsically-more-power-efficient)。

机器人常选ARM平台，是因为有丰富的嵌入式MCU与应用处理器、低功耗SoC及外设集成方案，适合电池供电、有限散热和紧凑空间。微控制器与运行Linux的应用处理器用途不同，不能把所有ARM平台混为一谈。x86平台则常适合需要成熟桌面软件、较强通用计算或现成PC硬件的场景。选择时应比较具体芯片的性能/功耗、接口、成本和软件支持；ARM不自动保证实时性，x86也不必然高功耗。

| 比较项 | NPU | GPU |
|---|---|---|
| 主要定位 | 面向神经网络计算的专用加速 | 通用并行计算及图形，亦广泛承担AI计算 |
| 常见优势 | 支持的模型和数据类型上可获得较好能效，适于端侧持续推理 | 并行吞吐高，通用性及训练/推理工具较丰富 |
| 常见约束 | 算子、张量形状与精度支持依厂商；模型转换/量化可能增加工作 | 性能依赖批量、带宽和调度；独立GPU还涉及传输及功耗成本 |
| 评价方式 | 检查实际模型能否完整运行、精度和端到端耗时 | 同样检查实际模型、数据传输、精度、耗时及功耗 |

NPU并非一定只能运行INT8，GPU也不只支持浮点；应查具体设备。若部分算子回退CPU，数据搬运和同步可能抵消峰值算力优势。TOPS需要结合精度、稀疏条件与实际利用率阅读，不能直接等同于应用速度。参考 [Intel CPU/GPU/NPU介绍](https://www.intel.com/content/www/us/en/products/docs/processors/cpu-vs-gpu.html)。本次MNIST只测CPU，不能用上述实测表推出NPU或GPU的排名。

## 附加题三：如何理解命中率的影响因素

“最主要因素”需要结合具体条件和实验结果判断。识别准确率、图像重投影残差、相对未来观测的预测误差，分别描述不同环节；命中率则是最终结果的统计。讨论两者的关系时，应区分局部指标与整体表现，并关注样本量和实验条件是否可比。

结合本项目，重投影残差反映几何拟合的一致性，检测覆盖率描述有检测输出的帧数比例，预测误差衡量与后续观测的差异。这些结果有助于评价已完成模块，但现有材料缺少独立的命中结果记录，因此尚不足以给各因素作可靠排序。我的认识是：结论应与指标的实际含义和证据范围相匹配。

## 附加题四：ROS 2 项目简介（单页篇幅）

**项目与功能。** 我选择ROS 2。它是一套用于开发机器人应用的开源软件库和工具，提供节点通信、接口定义及开发工具，便于组合传感器、算法和设备驱动。ROS 2运行于宿主操作系统之上，并非一个独立内核。项目入口：[ros2/ros2](https://github.com/ros2/ros2)。

**技术方案。** 应用分解成职责明确的节点，节点通过带类型的接口通信：Topic适合持续发布数据，Service适合请求/响应，Action用于有反馈、可取消的较长任务。这样可以将模块分配到不同进程，并以统一接口连接。参考 [ROS 2官方基本概念](https://repo.test.ros2.org/en/jazzy/Concepts/Basic.html)。

**评价。** 我认为其主要价值是减少机器人软件的集成成本：算法可以独立开发，接口明确后便于替换实现和协作调试。对于有数学建模与ACM背景的开发者，学习重点会从单个算法正确性扩展到消息类型、模块边界、时间与运行环境的一致性。代价是依赖和配置增多，系统故障可能来自通信或集成而非算法；使用ROS 2本身并不保证实时性或安全性。简单单机小程序未必需要引入完整框架。本评价基于公开文档阅读，不声称已完成ROS 2部署或实车验证。
